## Context

`/scheduler/tasks` 当前承载数据更新记录的筛选、分页和手动提交。后端将提供一个只读的调度状态集合，记录由 `scheduler_lease` 在 scheduler 首次 tick 后初始化，可能为空。

## Goals / Non-Goals

**Goals:**

- 在同一页面将调度状态与更新执行记录分开展示。
- 以现有 API 模块、dayjs 时间格式化和表格组件模式实现加载与刷新。
- 让用户看见调度提交状态而不将其误读为采集结果。

**Non-Goals:**

- 不创建路由或菜单项，不改变默认进入的更新记录页签。
- 不提供 Cron、租约或 scheduler 开关的编辑操作。
- 不把调度状态与更新任务记录拼接成同一张表。

## Decisions

### Decision 1: 在现有页面使用两个页签

页面默认显示“数据更新记录”，以保持当前加载和提交操作不变；选择“调度状态”时加载其独立表格。两个数据集的筛选、分页和刷新语义不同，使用页签比同表混排清晰。

### Decision 2: 新增轻量 API 客户端与独立查询状态

在 `src/api/dataUpdates.ts` 增加调度状态类型和 `getSchedulerSchedules()`，并在页面中维护独立的 loading 与数组状态。接口无分页，客户端不引入分页组件或筛选表单。

### Decision 3: 用明确列标题解释状态语义

表格显示作业名称、Cron、下次执行、最近提交时间、最近提交结果、租约持有者、租约到期和记录更新时间。`last_status` 列标题固定为“最近提交结果”，并在状态缺失时显示“-”；实际采集结果继续由“数据更新记录”呈现。

## Risks / Trade-offs

- [Risk] scheduler 尚未启动时空表会被理解为加载失败。→ 显示“暂无已初始化的调度记录”的空状态。
- [Risk] 后端接口未部署时页签无法展示。→ 复用当前错误提示模式并保留重新加载入口。
- [Risk] 屏幕较窄时字段较多。→ 延续既有可横向滚动的表格布局与溢出提示。

## Migration Plan

1. 前端与后端接口一同发布。
2. 回滚时移除页签和客户端调用，不影响已有更新记录功能。
